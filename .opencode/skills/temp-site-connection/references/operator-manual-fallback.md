# Operator-led manual fallback protocol (reference)

Moved out of `SKILL.md`. This protocol predates the live executor and is the operator-manual fallback, NOT the default; the agent-driven path is the flip pattern via the gated executor/CLI.

## Example: operator-proposed station-bridge handoff (candidate plan, not executed)

The operator proposed using Zulu 5S (`10.0.80.5`) as a temporary bridge toward Yankee5N, then forming a Yankee5S → Zulu5S link, restoring the Zulu AP, and adding OSPF. This is not yet a validated sequence: the names, roles, topology, and command syntax are hypotheses until checked against fresh inventory and device state. Critically, Yankee5S cannot associate to Zulu5S while Zulu5S is operating as a station. “Stage the station config” can only mean writing/readback of intended settings while association is pending; it is not link verification.

Before the first change, use this operator-led, stop-after-each-step protocol (this Yankee/Zulu sequence predates the live executor — it is the operator-manual fallback, NOT the default; the agent-driven path is the flip pattern above via the gated executor/CLI):

1. Freshly identify all endpoint devices by exact management IP and corroborate model, firmware, serial/MAC if available, role, and management route. Record source timestamps; reconcile future-dated/stale inventory. Confirm which radio is physically on each end, actual AP/ST roles, channel/band/protocol/security compatibility, and whether any alternative management path exists. If an identity, endpoint, or required link is ambiguous, stop.
2. Read and save full current config plus focused wireless/network settings and client/registration count for Zulu5S and both Yankee radios. Record a checksum/timestamp and a human-readable restore recipe. Confirm you can restore Zulu5S using a local/independent management path even after its wireless role changes. If its only management path is the link being changed, do not start. The management path must be a WIRED-side device at the reachable site (router/switch on the LAN, verified by IP + gateway + interface) — never management that itself traverses the radio link under change, and never the far-side radio as your only path.
3. Map the exact temporary path and its control-plane/data-plane dependency: which node can reach Yankee5S during the first handoff, and what path will remain after Zulu5S returns to AP. Ensure the intended Yankee5S settings can be written/read back while association is pending and that restoring Zulu does not strand management of Yankee5S. No guessed credentials, SSID, BSSID, key, interface, or commands.
4. Only after steps 1–3 pass, the operator manually performs the single agreed Zulu5S transition. This intentionally interrupts its associated clients under the standing authorization. Immediately inspect its state and the expected association to Yankee5N; verify management and record known/unknown interruption. If the expected association or management path fails, restore Zulu5S from its saved state before doing anything else.
5. While the temporary management path is known-good, the operator may make one separately reviewed Yankee5S station configuration change using the exact settings verified from Zulu5S's saved AP config. Read back the configuration. Do not claim association yet: Zulu5S is still a station, so its normal AP is unavailable. Confirm the current control path to Yankee5S will survive the next handoff.
6. Restore Zulu5S's exact saved AP config as the next controlled transition. Verify its AP role/BSSID/config and customer registrations recover. Only then check whether Yankee5S associates to that AP and whether the intended Yankee management path remains reachable. If Zulu customers do not recover promptly, prioritize restoring the donor AP and stop further changes.
7. If the radio handoff is stable and management reachability is preserved, separately read both routers' interfaces, addresses, OSPF instance/area/authentication/cost, routes, and filters. Check the curated pair `10.0.70.113/30` + `10.0.70.114/30` (`10.0.70.112/30`) for conflicts on every involved device. Record `operator-curated; Sheet not checked`. Only then agree a separate OSPF change; do not combine it with the radio transition.

At every step of THIS fallback protocol only, the operator performs the change; the agent reviews the supplied sanitized before/after configuration and read-only verification before suggesting the next step. Never paste credentials/private keys. A timed-out or ambiguous operation is an unknown result: inspect live state before retrying or restoring. No BGP, default route/origination, NAT, router-dead `.1/24`, customer CPE changes, or unrelated config is included.
